# Запуск игры через Docker Compose

Два контейнера: `server` с игровым сервером и `web` с Caddy и собранным клиентом. Node.js, pnpm, отдельные systemd-службы игры и каталог `/var/www/krunker` на VM не нужны. Сервер доступен только внутри сети Compose, наружу опубликованы TCP 80 и 443.

Контейнеры на локальном компьютере и на VM не запускались. Проверку полного запуска нужно выполнить на VM.

## Первый запуск на новой Ubuntu VM

Сначала отправь эти изменения в GitHub. Клонирование получает только опубликованные коммиты, а не файлы с твоего компьютера.

Если старый SSH-автодеплой включён, установи repository variable `DEPLOY_ENABLED=false` в GitHub. Существующий workflow управляет systemd и не подходит для контейнеров.

На VM под своим административным пользователем, не под `github-deploy`:

```bash
sudo apt-get update
sudo apt-get install -y git
git clone --branch main https://github.com/KrotovPetr/krunker.git krunker-docker
cd krunker-docker
bash scripts/setup-docker.sh
```

Если каталог `krunker-docker` уже существует, не клонируй поверх него. Перейди в существующий клон и проверь его содержимое. Закрытый репозиторий потребует доступа к чтению GitHub; не вставляй токен в URL клонирования.

Мастер запросит подтверждение установки Docker из официального apt-репозитория, предложит адрес сайта, соберёт образы и запустит контейнеры. Запускай мастер без `sudo`, необходимые административные команды он выполнит через `sudo` сам. На уже установленном Docker мастер проверяет наличие Compose и доступность движка, но не переустанавливает его.

Для тестового запуска по IP оставь адрес пустым. После запуска открой `http://ПУБЛИЧНЫЙ_IP_VM`. Такой HTTP-трафик не шифруется.

В облачной группе безопасности разреши TCP 80 и 443. Порты 2567 и 5173 не открывай. Учти, что опубликованные Docker-порты могут обходить UFW: ограничения задавай также на уровне облачной сети. [Установка Docker и ограничения firewall](https://docs.docker.com/engine/install/ubuntu/).

Если старый Caddy или другой сайт уже занимает 80/443, сначала реши, нужно ли его сохранять. Мастер не останавливает существующие службы. Для проверки рядом с ними можно задать в корневом `.env` другие порты:

```dotenv
SITE_ADDRESS=:80
HTTP_PORT=8088
HTTPS_PORT=8443
```

Тогда тестовый адрес будет `http://ПУБЛИЧНЫЙ_IP_VM:8088`; этот порт нужно разрешить в облачной группе безопасности. Не используй такие внешние порты для стандартного автоматического выпуска HTTPS-сертификата.

## Если Docker и Compose уже установлены

Из корня клона:

```bash
sudo docker compose build
sudo docker compose up -d --wait --wait-timeout 120
sudo docker compose ps
```

Первый запуск включает скачивание зависимостей и сборку, поэтому не будет мгновенным. Следующие сборки используют кеш. Образы сначала собираются полностью; работающие контейнеры меняются только на шаге `up`.

Сервер работает без root, с read-only файловой системой. Compose ждёт успешной проверки сервера перед запуском Caddy. Caddy имеет собственную проверку проксирования `/health`. Проверки не заменяют тест входа в комнату из браузера. [Ожидание готовности в Compose](https://docs.docker.com/compose/how-tos/startup-order/).

## Обновление

В том же клоне, под его владельцем:

```bash
git pull --ff-only
sudo docker compose build
sudo docker compose up -d --wait --wait-timeout 120
```

Выполняй команды последовательно. Если `pull` или сборка завершились ошибкой, не запускай следующий шаг. Комнаты находятся в памяти сервера и завершаются при его замене. Автоматического отката нет. `restart: unless-stopped` перезапускает завершившийся контейнер, но сам по себе не исправляет состояние `unhealthy`.

Для обновлений без сборки на VM подготовлен [Docker-автодеплой через GitHub Actions](DEPLOY_DOCKER_AUTO.md). Он публикует образы с тегом SHA и передаёт VM команду скачать и запустить нужную версию. Этот путь требует отдельной разовой настройки; команды выше описывают ручную сборку.

Не добавляй `github-deploy` в группу `docker` ради старого workflow: управление обычным Docker даёт практически root-доступ к машине. Для автоматизации нужно отдельно определить права и новый сценарий деплоя.

## HTTPS с доменом

Настрой A-запись домена на публичный IP VM. Если есть AAAA-запись, IPv6 тоже должен вести на эту VM. Оставь внешние порты 80/443 и задай в корневом `.env`:

```dotenv
SITE_ADDRESS=play.example.com
```

Примени настройку:

```bash
sudo docker compose up -d --wait --wait-timeout 120
```

Клиент собран с `VITE_SERVER_URL=same-origin` и берёт адрес сервера из страницы. При смене IP или переходе на HTTPS пересборка клиента не нужна. Обычный локальный `pnpm dev` и существующий `VITE_SERVER_URL` сохраняют прежнее поведение.

Сертификаты хранятся в именованных томах `caddy_data` и `caddy_config`. Не выполняй `docker compose down -v`, если хочешь их сохранить.

## Диагностика

```bash
sudo docker compose ps
sudo docker compose logs --tail=100
sudo docker compose exec -T web wget -q -O - http://127.0.0.1:8080/health
```

После внутренней проверки открой публичный сайт, создай комнату и войди вторым игроком. При необходимости проверь доступ к `/health` по публичному адресу.

Остановить игру, сохранив сертификаты:

```bash
sudo docker compose down
```
