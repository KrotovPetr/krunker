# Автоматические обновления Docker

После настройки: `git push origin main` → проверки → Docker-образы в GHCR → проверка контейнеров в GitHub → SSH на VM → скачивание и замена контейнеров. На VM не нужны Node.js, pnpm или сборка исходников.

Код подготовлен, но новый workflow, мастер и тесты в этой сессии не запускались по просьбе пользователя. Секреты и настройки GitHub автоматически не изменялись, файлы не коммитились и не отправлялись.

## Разовая настройка

### 1. Выбери Docker в GitHub

В репозитории открой Settings → Secrets and variables → Actions → Variables. Создай или обнови repository variables:

- `DEPLOY_MODE=docker`;
- `DEPLOY_ENABLED=false`.

Отправь подготовленные файлы в `main`. При `DEPLOY_MODE=docker` образы собираются даже с выключенным деплоем. Старый systemd-job при этом пропускается.

Workflow публикует `ghcr.io/krotovpetr/krunker-server:<SHA>` и `ghcr.io/krotovpetr/krunker-web:<SHA>` для Linux amd64 и arm64. Для публикации используется встроенный `GITHUB_TOKEN` с `packages: write`, отдельный секрет для записи в registry не нужен. [Публикация образов через Actions](https://docs.github.com/en/actions/tutorials/publish-packages/publish-docker-images).

### 2. Подготовь VM

Предполагается, что Docker с Compose уже установлен, а пользователь `github-deploy` и его SSH-ключ настроены по предыдущей инструкции. Если Docker ещё нет, начни с [первого запуска](DEPLOY_DOCKER.md).

На VM под административным пользователем, из клона проекта с этими файлами:

```bash
git pull --ff-only
bash scripts/setup-docker-autodeploy.sh
```

Если `git pull` завершился ошибкой, сначала разбери её. Не запускай мастер из устаревшего клона. Мастер надо запускать без `sudo`, административные команды он вызовет сам после подтверждения.

Мастер проведёт разовую настройку:

- сохранит адрес и порты в `/etc/krunker/deploy.env`;
- установит root-owned Compose и скрипт обновления;
- заменит команду, которую вызывает существующий SSH-ключ, сохранив резервную копию старых установленных файлов;
- разрешит `github-deploy` через sudo вызывать только этот скрипт с проверяемым SHA;
- предложит вход VM в GHCR и покажет, где включить обновления.

`authorized_keys` и SSH-ключи не перезаписываются. В группу `docker` пользователь не добавляется. Production Compose хранится отдельно от доступного для записи клона, поэтому SSH-ключ не может подставить свой Compose с доступом к файловой системе хоста. Скрипт принимает только один SHA, а путь образов задаёт администратор.

Приватные пакеты GHCR требуют personal access token classic с `read:packages` и доступом к этим пакетам. Мастер вводит его скрыто и передаёт через `--password-stdin`; Docker сохраняет credentials в `/root/.docker/config.json`. Не добавляй токен в репозиторий и не отправляй его в чат. Для публичных пакетов или уже настроенного входа этот шаг можно пропустить. Пакеты автоматически публичными не становятся. [Доступ к GHCR](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry).

TCP 22 должен быть доступен GitHub runner. Если разрешён только домашний IP, деплой не подключится. Не расширяй доступ, пока не проверен административный SSH-вход только по ключам. TCP 80/443 нужны сайту, TCP 2567 наружу не публикуется.

Если уже запущен Compose-проект `krunker`, обновление заменит его контейнеры, сохранив именованные тома Caddy. Отдельный systemd-Caddy или другой сайт на 80/443 мастер не останавливает; такой конфликт нужно решить до включения деплоя.

### 3. Включи обновления

Проверь существующие GitHub Secrets:

- `DEPLOY_HOST`: публичный IP или SSH-имя VM без схемы и порта;
- `DEPLOY_SSH_KEY`: ранее подготовленный приватный ключ Actions → VM;
- `DEPLOY_KNOWN_HOSTS`: ранее проверенный публичный SSH-ключ VM с её адресом.

Установи repository variables `DEPLOY_MODE=docker` и `DEPLOY_ENABLED=true`. Затем отправь следующий коммит в `main` или выбери Re-run all jobs у запуска `Checks`, созданного push текущего `main`.

Ожидаемые job: `check` → `Build and verify Docker images` → `Deploy Docker to VM`. Лог последнего должен закончиться `Deployed <SHA>`. Проверь публичный сайт и создание комнаты с двумя игроками. Браузерные e2e временно исключены из общего CI и не блокируют деплой; сами тесты и команда `pnpm test:e2e` сохранены. Проверка контейнеров на runner проверяет HTTP, здоровье и отдачу страницы, но не игровой WebSocket через Caddy. ARM64-образы собираются, проверка запуска на runner выполняется на amd64.

После этого обновление игры сводится к обычному push в `main`. Незакоммиченные файлы на компьютере не деплоятся. Pull requests и другие ветки не меняют VM.

## Что происходит при ошибке

- Ошибка проверок, сборки или проверки контейнеров в GitHub не запускает деплой на VM.
- Ошибка скачивания образов оставляет работающие контейнеры нетронутыми.
- Неуспешный запуск новой пары контейнеров вызывает попытку вернуть предыдущий успешно установленный SHA. Даже успешный откат оставляет job красным.
- При самом первом переходе с ручной сборки предыдущий SHA ещё не записан, автоматического отката нет. Откат также не гарантируется при ошибке самого Docker, нехватке диска или удалённых старых образах.

Текущие комнаты заканчиваются при замене сервера. Это не zero-downtime deployment. SHA используется как тег, не как immutable digest; повторная сборка того же SHA может обновить его образы. При повторном деплое того же записанного SHA автоматического отката на него нет.

Скрипт сохраняет текущий успешный SHA в `/var/lib/krunker-deploy/current.sha`, предыдущий в `previous.sha`. Старые образы автоматически не удаляются, поэтому периодически проверяй свободное место. Не удаляй образы, необходимые для отката, и не используй `down -v`, если нужно сохранить сертификаты.

## Настройки после переключения

Адрес и порты меняются через `sudoedit /etc/krunker/deploy.env`, а не `.env` в клоне. После изменения отправь новый коммит или повтори текущий деплой.

Root-owned Compose и скрипты на VM намеренно не перезаписываются обычным push. Если меняются именно они, выключи `DEPLOY_ENABLED`, обнови административный клон, снова запусти мастер и затем включи деплой. Существующий `deploy.env` мастер сохраняет.

Диагностика на VM:

```bash
sudo cat /var/lib/krunker-deploy/current.sha
sudo docker ps --filter label=com.docker.compose.project=krunker
sudo docker system df
```

Ручной повтор или возврат к известному SHA, если его образы ещё доступны в GHCR:

```bash
sudo /usr/local/sbin/krunker-docker-deploy ВСТАВЬ_ПОЛНЫЙ_SHA_КОММИТА
```

Для временной остановки автоматических обновлений поставь `DEPLOY_ENABLED=false`. Проверки и публикация образов продолжат работать. Не переключай обратно на systemd, пока установлен Docker-wrapper: для обратной миграции потребуется вернуть старый скрипт и конфигурацию.
